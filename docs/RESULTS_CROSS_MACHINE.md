# 跨机通讯延迟对比：ROS 2 FastDDS vs Zenoh（Orin ↔ 5060Ti 工作站）

在 NVIDIA Jetson AGX Orin（ROS 2 Humble）与 i9-14900HX 工作站（ROS 2 Jazzy）之间，通过同一 2.4 GHz Wi-Fi 局域网，用**完全相同**的 rclpy 发布/订阅代码，分别以 FastDDS 直连和 Zenoh（zenoh-bridge-ros2dds 1.10.2）传输，测量相机图像、激光雷达点云与 25 关节位置的单向端到端延迟。

## 概要

- **25 关节位置（200 B，20 Hz）**：FastDDS P50 6.6 ms / 丢帧 7.9%，Zenoh P50 6.1 ms / 丢帧 3.8%。
- **25 关节位置（200 B，100 Hz）**：FastDDS P50 3.6 ms / 丢帧 22.7%，Zenoh P50 4.4 ms / 丢帧 32.7%。
- **彩色图 640×480 rgb8（922 KB，0.5 Hz）**：FastDDS P50 293.2 ms / 丢帧 8.3%，Zenoh P50 390.4 ms / 丢帧 28.3%。
- **激光雷达 XYZ 点云（1.38 MB，0.25 Hz）**：FastDDS P50 365.3 ms / 丢帧 16.7%，Zenoh P50 515.9 ms / 丢帧 53.3%。

结论：在 45 Mbps 的 2.4 GHz 链路上，**延迟由链路串行化主导**，两种中间件的 P50 差异为 +22%（100 Hz 关节）、−8%（20 Hz 关节）、+33%（彩色图）、+41%（点云）；Zenoh 在彩色图、点云与 100 Hz 关节流上的丢帧率都更高（20 Hz 关节流除外）。机内实验里那种 0.4–4.9 ms 的绝对量级在跨机场景中无法保持。

## 1. 实验环境

| 项目 | Orin | 5060Ti 工作站 |
| --- | --- | --- |
| 硬件 | NVIDIA Jetson AGX Orin，8 核 ARMv8，30 GB 内存 | Intel i9-14900HX，32 线程，62 GB 内存 |
| 系统 | Ubuntu 22.04.5 LTS，内核 5.15.148-tegra | Ubuntu 24.04.4 LTS，内核 7.0.0-38-generic |
| ROS 2 | Humble，rmw_fastrtps_cpp，Fast DDS 2.6.12 | Jazzy，rmw_fastrtps_cpp，Fast DDS 2.14.6 |
| 网络 | Wi-Fi 192.168.0.118，2.4 GHz 信道 1，40 MHz，-33 dBm | Wi-Fi 192.168.0.117（同一 AP），-32 dBm |
| 角色 | 发布端，读取 RealSense / RSLiDAR bag | 订阅端，记录到达时间戳 |

链路基线（同批次实测）：iperf3 单流 TCP **45.6 Mbps**；跨机 ICMP RTT 最小 2.3 ms、中位 4–5 ms、偶发 100–200 ms 尖峰；两机 Wi-Fi 省电已关闭，UDP 接收缓冲提高到 32 MB。

## 2. 方法

```
  Orin / Humble                                    5060Ti 工作站 / Jazzy
  ┌──────────────┐    Wi-Fi 2.4 GHz, 45 Mbps   ┌──────────────┐
  │ xbench_pub   │ ──────────────────────────► │ xbench_sub   │
  └──────────────┘                             └──────────────┘
        │                                             ▲
        │ Zenoh 路径（DDS domain 77 → 78）             │
  ┌──────────────┐    Zenoh/TCP    ┌──────────────┐      │
  │ bridge 1.10.2│ ──────────────► │ bridge 1.10.2│ ─────┘
  └──────────────┘                 └──────────────┘
```

- **测量口径**：发布端从原始 bag 读取固定帧窗口，按目标速率重放，在 `publish()` 前把 `header.stamp` 设为当前 `CLOCK_REALTIME`；订阅端在回调入口取时间戳，延迟 = 到达时间 − 发送时间戳。测量包含序列化、传输、反序列化与回调调度。
- **QoS**：best_effort、keep_last(1)、volatile；与传感器话题的常用配置一致。
- **速率**：为了不把 45 Mbps 链路打满（打满后队列延迟会掩盖中间件差异），大载荷按 0.5 Hz（彩色）/ 0.25 Hz（点云）发送；关节流分别测 20 Hz 与 100 Hz。
- **时钟校正**：两机各自用公网 NTP，实测相对偏移在数十至数百毫秒间漂移，不能直接比较绝对时间。测量期间每 200 ms 发一个带 nonce 的 UDP 往返探针，只保留 RTT 接近最小值的样本，按消息时间戳插值出该时刻的偏移；nonce 用于丢弃迟到的旧回复（否则会被误判成时钟跳变）。剩余不确定度约 ±1 ms。
- **Zenoh 部署**：官方 `zenoh-bridge-ros2dds` 1.10.2，Orin 侧 router（DDS domain 77），工作站侧 client（DDS domain 78），两者用 Zenoh/TCP 相连。两侧 DDS domain 不同，不存在绕过 Zenoh 的 DDS 直连；应用层代码与 FastDDS 组完全相同。
- **为什么不用 `rmw_zenoh`**：Humble 的 rmw_zenoh 0.1.11 与 Jazzy 的 0.2.11 话题 keyexpr 不兼容——前者以 `TypeHashNotSupported` 结尾，后者用 `RIHS01_…` 类型哈希，订阅端收不到任何数据；这是跨发行版部署 Zenoh 时必须先解决的工程问题。因此改用 bridge 方案。

### 3.1 相对 FastDDS 的变化

| 数据 | P50 变化 | P95 变化 | 丢帧率变化（百分点） | 链路串行化下限 ms |
| --- | ---: | ---: | ---: | ---: |
| 25 关节位置 200 B, 20 Hz | -8.8% | -15.6% | -4.1 | 0 |
| 25 关节位置 200 B, 100 Hz | +22.9% | +35.0% | +10.0 | 0 |
| 彩色图 640×480 rgb8 922 KB, 0.5 Hz | +33.1% | +23.1% | +20.0 | 162 |
| 激光雷达 XYZ 点云 1.38 MB, 0.25 Hz | +41.2% | +50.9% | +36.7 | 242 |

链路串行化下限 = 载荷 × 8 ÷ 45.6 Mbps，是单帧在空口上占用的最短时间。

### 3.2 对照实验：Zenoh 链路从 TCP 换成 UDP

Zenoh 的协议本身不绑定 TCP，bridge 的链路可以用 `udp/` 端点。保持其余配置不变，只把工作站←→Orin 的 Zenoh 链路换成 UDP，重测彩色图：

| 彩色图 922 KB @0.5 Hz | P50 ms | P95 ms | P99 ms | 丢帧率 |
| --- | ---: | ---: | ---: | ---: |
| FastDDS（best-effort UDP） | 293.2 | 565.8 | 1,738.6 | 8.3% |
| Zenoh bridge，TCP（默认） | 390.4 | 696.4 | 744.9 | 28.3% |
| Zenoh bridge，UDP | 351.0 | 578.2 | 1,666.4 | 6.7% |

换成 UDP 后 Zenoh 的 P50 从 390 ms 降到 351 ms，丢帧率从 28.3% 降到 6.7%（低于 FastDDS 的 8.3%），P95 与 FastDDS 持平。也就是说，上一节里 Zenoh 在大载荷上的劣势，**主要来自 TCP 的可靠传输与队头阻塞，而不是 Zenoh 协议本身**；在丢包率高的无线链路上，用可靠传输承载 best-effort 的传感器流是配置错误。

## 4. 讨论

1. **大载荷时延由空口决定，而非中间件。** 922 KB 彩色图的链路下限约 162 ms，实测 FastDDS P50 293 ms、Zenoh 390 ms；1.38 MB 点云下限约 242 ms，实测 365 ms / 516 ms。剩余部分来自 UDP 分片/重传、AP 排队和接收端拷贝。在这个区间里比较“中间件谁快”意义有限，选型更应看丢帧与可预测性。
2. **默认 TCP 配置下 Zenoh 更慢、丢得更多。** bridge 走 TCP，单帧被拆成多个 Zenoh 分片顺序发送，任何一个分片重传都会阻塞后续分片（队头阻塞），表现为 P95/P99 明显变长、在 0.25 Hz 点云上丢帧率达到 53%。FastDDS 的 best_effort UDP 允许整帧丢弃但不阻塞后续帧。但 3.2 的对照实验说明这是**传输选择**而非协议能力的差异：把 Zenoh 链路换成 UDP 后，P50 与丢帧率都回到 FastDDS 的水平。
3. **小载荷时两者处于同一量级。** 200 B 关节数据在 20 Hz 下 FastDDS/ Zenoh 的 P50 为 6.6 / 6.1 ms，差异小于单次运行的波动（不同重复之间 P50 可差 1 ms 以上）；100 Hz 下为 3.6 / 4.4 ms，Zenoh 高约 22%，同时丢帧率高约 10 个百分点。20 Hz 与 100 Hz 的排序相反，说明这一量级的差异已接近测量与链路抖动的分辨率，不宜据此断言优劣。
4. **与机内结果对比。** 同一台 Orin 上，DAVOS_SIM 共享内存为 0.4–0.6 ms，ROS 2（含同机共享内存传输）为 1.5–4.9 ms；跨机后即使只有 200 B，也退化到 3–7 ms，大载荷则是数百毫秒。瓶颈从“中间件/拷贝”彻底转移到“空口”。
5. **工程结论。** 跨机部署 Zenoh 时，`rmw_zenoh` 的跨发行版不兼容是目前最实际的障碍；在 Humble+Jazzy 混布场景下，zenoh-bridge-ros2dds 是可行替代，但会引入两端各一次 DDS↔Zenoh 转换。

## 5. 局限

- 链路为单频段 2.4 GHz（信道 1、40 MHz、老式 WPA1/WPA2 AP），实测 TCP 吞吐仅 45 Mbps；结论不能外推到 5 GHz 或千兆有线。
- 为保证时钟探针可用，大载荷速率被降到 0.5 / 0.25 Hz，每次运行只有 30 / 15 帧，丢帧率与高分位数的置信区间较宽；点云 Zenoh 有一次运行只收到 1/15 帧。
- 两机时钟由公网 NTP 校准，相对偏移在运行中仍会漂移数十毫秒；结果依赖 UDP 探针插值，绝对延迟不确定度约 ±1 ms，小载荷的细微差异落在该误差内。
- 大载荷高速率（彩色 2 Hz、点云 1 Hz）的尝试因链路饱和导致时钟探针失真，相关数据未纳入本报告；那组实验只能说明“打满链路后延迟会到秒级”。
- Zenoh 路径为 bridge 部署（DDS→Zenoh→DDS），比原生 `rmw_zenoh` 多两跳本地 DDS，对 Zenoh 略不利；这是跨发行版约束下的唯一可行方案。
- 订阅端为 Python rclpy，回调与 CSV 写入开销已计入；发布端从 bag 解码后重发布，解码本身在打点之前，不计入延迟。

## 6. 复现

```bash
# Orin（发布端）
cd ~/xbench && bash run_pub.sh fastdds color05 <bag> 0.5 60 /tmp/pub.csv
# 工作站（订阅端）
cd ~/xbench && bash start_sub.sh fastdds color05 85 /tmp/sub.csv
# Zenoh 路径：先起两侧 bridge
bash bridge_orin.sh start   # Orin, DDS domain 77, router
bash bridge_ws.sh start     # 工作站, DDS domain 78, client
```
