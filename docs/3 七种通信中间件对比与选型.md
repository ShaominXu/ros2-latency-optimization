# 3 七种通信中间件对比与选型

Fast DDS · Cyclone DDS · Zenoh · iceoryx2 · eCAL · SIM（DAVOS_SIM）· Agnocast

本文只讨论架构定位、能力边界与选型依据，不含实测数据。七种方案里只有 Fast DDS、Cyclone DDS、Zenoh 是 ROS 2 的 RMW 实现；iceoryx2 与 eCAL 是独立中间件，经 rmw 层接入；Agnocast 是 ROS 2 原生旁路层；SIM 是研究原型。七种方案在同一台 AGX Orin 上的同帧延迟、漏帧与 CPU/RSS 结果见 `4 五种中间件延迟对比.md`；Fast DDS / CycloneDDS 的机内对比与 Data-sharing 可用性验证见 `6 ROS 2 中间件机内延迟对比.md`。

## 一、范围与读法

七种方案不是七个平行选项，按"对系统改动的深度"分四类。先确定能接受哪一种改动，再谈性能。

| 类别 | 方案 | 本质 | 接入 ROS 2 的方式 |
| --- | --- | --- | --- |
| A 换 RMW | Fast DDS、Cyclone DDS、Zenoh | 替换传输栈，应用代码基本不改 | `RMW_IMPLEMENTATION` |
| B 换栈 | iceoryx2、eCAL | 自带 API 与生态的共享内存 pub/sub | 原生 API，或第三方/官方 rmw 层 |
| C 打旁路 | Agnocast | 不改 ROS、不换 RMW，只接管指定话题 | 改代码用 `agnocast::` API，bridge 与 DDS 互通 |
| D 研究原型 | SIM（DAVOS_SIM） | 只解决"最新帧从传感器到算法" | 无，自研 `SIM_*` API，需自己桥接 |

Tier 为 REP-2000 的支持等级，按"平台 + 中间件"两级取较低者：Tier 1 持续执行 CI、性能测试与打包，是发布把关对象；Tier 2 周期性 CI、二进制包不保证；Tier 3 仅凭社区反馈判定可用、通常只有源码构建。**Tier 只代表测试与维护承诺，不是性能排序。**

A 类与 B 类的关键差别：A 类是"还在这张 ROS 图里，只是换了底层实现"，B 类是"整个进程搬到另一张图上"。这决定了互操作、工具链和调试方式，详见 3.2 节。

## 二、七种方案总览

| 方案 | 类别 | 核心定位 | 支持等级与平台（Humble / Jazzy） | 与 ROS 2 的关系 |
| --- | --- | --- | --- | --- |
| Fast DDS | A | DDS/RTPS；SHM transport、Data-sharing | Tier 1（默认）；Humble 2.6.x / Jazzy 2.14.x；全平台全架构 | 默认 RMW |
| Cyclone DDS | A | DDS/RTPS；可选 iceoryx 共享内存集成 | Tier 1；Humble / Jazzy 均有官方包 | 独立 RMW 实现 |
| Zenoh | A | 分布式 pub/sub + query + 路由（非 DDS） | Kilted 起 Tier 1；Humble / Jazzy 有 `rmw_zenoh_cpp` 包 | 非 DDS 的 RMW |
| iceoryx2 | B | 原生零拷贝共享内存 IPC（Rust） | 非 ROS RMW；Linux/macOS/Windows/FreeBSD | 经第三方 `rmw_iceoryx2` 或原生 API |
| eCAL | B | 共享内存 + 网络 pub/sub，含监控/录制/回放 | 非 ROS RMW；Linux/Windows 为主 | 经官方 `rmw_ecal` 或原生 API |
| SIM（DAVOS_SIM） | D | 共享内存双缓冲、最新帧优先 | 非 RMW，无 REP-2000 等级；论文未声明平台范围 | 无集成，需自建桥接 |
| Agnocast | C | rclcpp 兼容的真零拷贝旁路 | 非 RMW；Humble / Jazzy，Ubuntu 22.04/24.04，仅 C++ | 与现有 RMW 并存，逐话题改造 |

## 三、能力矩阵

### 3.1 零拷贝与消息类型

| 方案 | 零拷贝机制 | 支持无界 ROS 消息 | 跨机 |
| --- | --- | --- | --- |
| Fast DDS | SHM transport 仍有一次拷贝；Data-sharing 为真零拷贝，但要求 bounded 类型 | 否（`Image`/`PointCloud2` 的 `data` 是无界 sequence） | 支持（UDP/TCP） |
| Cyclone DDS | 无真零拷贝；共享内存需 iceoryx 集成 | 否（同上） | 支持 |
| Zenoh | 无（定位是跨网络路由与查询） | 支持（序列化照旧） | 支持（原生优势） |
| iceoryx2 | loaned sample 借还：省掉拷贝，但仍要序列化进借出的共享内存 | 支持（需类型映射） | 否（同机为主） |
| eCAL | 默认 SHM 有 2 次 memcpy；full zero-copy（5.12 起）需低层 API 且默认关闭 | 支持（自行序列化，protobuf 或裸结构） | 支持（UDP/TCP） |
| SIM（DAVOS_SIM） | 双缓冲 + POSIX 共享内存；读者拷回本地工作区 | 不适用（只传裸字节，不解码 ROS 类型） | 否（论文中另接 DDS 桥） |
| Agnocast | 堆分配重定向到固定虚拟地址的共享内存 + 同偏移只读映射 + 内核态引用计数，无序列化 | 是（rosidl 结构直通） | 仅经 bridge 回落 DDS（该段无零拷贝） |

### 3.2 部署依赖与可观测性

| 方案 | 额外依赖 / 特权 | ROS 2 工具可见性 | 成熟度 |
| --- | --- | --- | --- |
| Fast DDS | 无 | 完全（list / info / echo / bag） | 稳定，默认实现 |
| Cyclone DDS | 无 | 完全 | 稳定 |
| Zenoh | 需 router 进程 | 完全（走 `rmw_zenoh`） | 稳定，Tier 1（Kilted 起） |
| iceoryx2 | 无 | 换 RMW 后在其图内可见，但 `rmw_iceoryx2` 的 Graph 功能未完成，`ros2 topic list` 不可靠；原生 API 不可见 | 活跃；ROS 集成 alpha |
| eCAL | 无（无中心 broker） | 换 `rmw_ecal` 后可见；原生 API 的话题不进 ROS 图 | Apache-2.0，工具链完整；`rmw_ecal` 缺维护者 |
| SIM（DAVOS_SIM） | 无 | 不可见 | 研究原型，个人仓库，无 license |
| Agnocast | `agnocast_kmod` 内核模块 + `LD_PRELOAD` heaphook | 部分：标准命令只能看到 DDS 侧，需 `list_agnocast` 等专用动词 | Autoware 生态在用，实验性 |

## 四、优缺点与应用场景对比

| 方案 | 优势 | 局限 | 典型应用场景 |
| --- | --- | --- | --- |
| Fast DDS | 生态最完整、QoS 齐全、默认可用；SHM transport 无需调参 | 端到端仍有序列化与一次拷贝；Data-sharing 受 bounded 限制 | 现有 ROS 2 项目；需要兼容性的生产部署 |
| Cyclone DDS | 标准 DDS、Tier 1；适合作为独立基线 | 大载荷接收侧成本高；共享内存非默认路径 | DDS 互操作对照；多厂商备份 |
| Zenoh | 跨网络路由与查询能力强；多机器人/边缘友好 | 同机 IPC 不占优；QoS 映射需验证 | 跨机、无线网络、边缘计算 |
| iceoryx2 | 借还式零拷贝，省掉大消息搬用；适合一对多 | ROS 集成 alpha；样本生命周期要自己管；仅同机 | 同机多进程感知；图像/点云广播 |
| eCAL | 同机共享内存与跨机并存；监控/录制/回放生态成熟 | 需自行序列化；全链路零拷贝要低层 API 且默认关闭；rmw 层缺维护者 | 测试台架、数据采集、多传感器融合 |
| SIM | 保留原生数据布局；实现简单；新鲜度优先 | 仍有两次拷贝；覆盖策略与并发安全待证明；无 license | 研究"新鲜度 vs 完整交付"的上限 |
| Agnocast | 唯一同时做到真零拷贝 + 无界消息 + 保留 ROS 2 编程模型 | 需内核模块与全局 heap hook；仅同机同 namespace；ABI 强约束；生态与工具仍在补齐 | 同机大消息感知链路，且能装内核模块的部署环境 |

## 五、选型建议

| 你的约束 | 首选 | 备选 | 不建议 |
| --- | --- | --- | --- |
| 生态与交付优先、不想改代码 | Fast DDS 默认（SHM 已默认启用） | Cyclone DDS（仅作对照） | 为"降延迟"而换 RMW |
| 跨机 / 多机器人 | Zenoh、Fast DDS UDP | — | 任何 SHM 方案（跨机没有零拷贝） |
| 同机大消息、可改应用、要录制回放与监控 | eCAL | iceoryx2 | SIM（无 license、无生产保证） |
| 必须保留 ROS 2 节点与消息、要真零拷贝、能装内核模块 | Agnocast | 改 `rmw_fastrtps` + 定长消息（成本更高） | 继续在 Data-sharing 上花时间（Humble 上打不开） |
| 研究新鲜度与完整交付的权衡 | SIM | — | 生产部署 |
| 低算力平台的传感器直通 | SIM 思路（原生布局 + 最新帧） | eCAL 的低 CPU 路径 | 通用 DDS + 大消息 + 多读者 |

三句话概括：**能改代码就换栈（eCAL / iceoryx2），不能改代码就只能接受 DDS 的编解码成本；中间地带目前只有 Agnocast 一条路，代价是内核权限与 ABI 约束。** 换 RMW 的收益通常小于"确认 SHM 已生效 + 收敛 QoS + 调调度"的收益，先把后三件事做完再谈换栈。

## 六、未纳入正文的对照项

| 方案 | 核心定位 | 支持等级与平台 | 未纳入原因 |
| --- | --- | --- | --- |
| Connext DDS（`rmw_connextdds`） | 商业 DDS/RTPS、DDS Security | Tier 1；Ubuntu/Windows/macOS，不含 arm64 | 商业许可（研究/非商用免费）；实验平台 Orin 为 arm64，不在支持矩阵；与 Fast DDS 同族，不引入新机制 |
| GurumDDS（`rmw_gurumdds_cpp`） | GurumNetworks 的 DDS 实现 | Tier 3；Ubuntu/Windows，不含 arm32 | 官方无 CI、缺陷不承诺修复；无共享内存主线；公开资料不可得 |
| Fast DDS 动态变体（`rmw_fastrtps_dynamic_cpp`） | 运行时类型自省的变体 | Tier 2；全平台全架构 | 与 `rmw_fastrtps_cpp` 共用传输层，单列构成重复计数 |

## 七、资料链接

### 1. SIM（Sensor-in-Memory）

- **定位**：研究型同机通信方案，保留 `cv::Mat` / PCL 原生布局，用有界双缓冲做"最新帧"通道，强调 freshness 而非完整交付。
- **机制**：每个传感器流对应一块命名的 POSIX 共享内存，含头部与两个数据缓冲；写者填充后台缓冲、更新元数据后切换 `front_idx`，读者按索引取帧并复制到本地工作区。库接口为 `SIM_writerInit` / `SIM_writeData` / `SIM_readerInit` / `SIM_readData` / `SIM_destroy`。
- **接入 ROS 2**：没有集成。跨 ECU 仍走 DDS，需要自己写桥接节点。
- **主要限制**：默认路径仍有两次 memcpy（写共享内存、读回工作区），因此单帧耗时仍随消息大小增长；可能覆盖旧帧，缓冲复用的并发安全缺少严格证明（release/acquire 只保证可见性，不保证读者正在使用的缓冲不被覆盖）；无 license、无文档，与论文实验版本的对应关系待核实。
- **资料**：论文《A Faster and More Reliable Middleware for Autonomous Driving Systems》 https://arxiv.org/abs/2510.11448 ；代码 https://github.com/Croquembouche/DAVOS_SIM （Public，未附许可证）。

### 2. Eclipse iceoryx2

- **定位**：Rust 实现的零拷贝数据平面，在共享内存中传递样本引用，提供 pub/sub、event、request-response 等模式，C/C++/Python 绑定。
- **机制**：发布者从共享内存分配器"借出"（loan）样本并原地填写，订阅者拿到样本引用后归还；省掉的是搬运，不是序列化。
- **接入 ROS 2**：第三方 `rmw_iceoryx2`（ekxide，Apache-2.0）把它做成 RMW；原生 API 则需要自己写桥。
- **主要限制**：ROS 集成处于 alpha，功能表里 Graph、Server-Client、Event 仍是建设中；样本生命周期需要应用管理（借出必须归还，否则池会耗尽）；定位是同机 IPC，跨机不支持。
- **资料**：https://iceoryx.io/ ；https://github.com/eclipse-iceoryx/iceoryx2 ；https://github.com/ekxide/rmw_iceoryx2

### 3. Eclipse eCAL

- **定位**：enhanced Communication Abstraction Layer，同机共享内存 + 跨机 UDP/TCP 的 pub/sub 与 client/server，配 Monitor、Recorder、Player、Sys 等工具链。
- **机制**：默认 SHM 路径是发布者写一次共享内存、每个订阅者再拷一次；5.10 起支持发布侧零拷贝、5.12 起支持全链路零拷贝，但**默认关闭**，需要用 `CPayloadWriter` 之类的低层 API 直接写共享内存。开启全链路零拷贝后，发布者会被慢订阅者阻塞，且与 multibuffering 互斥。
- **接入 ROS 2**：官方 `rmw_ecal`（Apache-2.0），有 dynamic 与 proto 两种实现——dynamic 更快但不进 eCAL 生态（Monitor 只能看到二进制数据），proto 版配合 `rosidl_typesupport_protobuf` 才能被原生 eCAL 工具解码。
- **主要限制**：需要自行序列化，与 rosidl 类型体系不是原生映射；`rmw_ecal` 官方声明已到维护能力上限、正在招维护者，版本兼容需自行验证。
- **资料**：https://eclipse-ecal.github.io/ecal/ ；https://github.com/eclipse-ecal/ecal ；零拷贝说明 https://github.com/eclipse-ecal/ecal/blob/master/doc/rst/advanced/layers/shm_zerocopy.rst ；https://github.com/eclipse-ecal/rmw_ecal

### 4. Eclipse Zenoh

- **定位**：把 pub/sub、query 与分布式数据访问融合在一起的协议与实现，强项是跨主机、多机器人、边缘网络的路由。
- **机制**：不是 DDS，没有 DDS 的发现与 QoS 模型；通过 router 组网，同机也走同一套路径。
- **接入 ROS 2**：官方 `rmw_zenoh_cpp`，Humble / Jazzy 有包，Kilted 起列入 Tier 1。
- **主要限制**：同机极致 IPC 不是它的强项；QoS 语义与 DDS 的映射、发现开销、丢包行为都需要按目标场景验证；部署多一个 router 进程。
- **资料**：https://zenoh.io/ ；https://github.com/eclipse-zenoh/zenoh ；https://github.com/ros2/rmw_zenoh

### 5. eProsima Fast DDS / Data-sharing

- **定位**：标准 DDS/RTPS 实现，ROS 2 默认 RMW。需要区分三个不同概念：Shared Memory Transport、Data-sharing Delivery、应用层 zero-copy。
- **机制**：SHM transport 只是把 RTPS 报文放进共享内存，仍有一次拷贝和序列化/反序列化；Data-sharing Delivery 才是免序列化的真零拷贝，但要求类型是 bounded。
- **接入 ROS 2**：默认，无需配置；`FASTDDS_BUILTIN_TRANSPORTS` 可裁剪传输，XML profile 可调 QoS。
- **主要限制**：`sensor_msgs/Image`、`PointCloud2`、`Float32MultiArray` 的 `data` 结构上是无界 sequence，按设计不满足 Data-sharing 条件；Humble 的 `rmw_fastrtps_cpp` 还会在加载 XML 后无条件调用 `data_sharing().off()`，即配置层面也打不开（这是源码行为，不是参数问题）。
- **资料**：https://fast-dds.docs.eprosima.com/ ；https://github.com/eProsima/Fast-DDS ；Humble 版 Data-sharing 约束 https://fast-dds.docs.eprosima.com/en/2.6.x/fastdds/transport/datasharing.html ；https://github.com/ros2/rmw_fastrtps

### 6. Eclipse Cyclone DDS

- **定位**：开源 DDS 实现，ROS 2 的另一个 Tier 1 选择，常作为 Fast DDS 的独立对照。
- **机制**：同为 DDS/RTPS；共享内存能力依赖 iceoryx 集成，与 Fast DDS 的 SHM transport 不是同一条路径。
- **接入 ROS 2**：`RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`。
- **主要限制**：默认走 UDP（含回环），大载荷的分片/重组成本在接收侧；要缩小差距需调 RTPS 分片等参数，且调优效果依版本与网卡而异。
- **资料**：https://cyclonedds.io/ ；https://github.com/eclipse-cyclonedds/cyclonedds ；https://github.com/ros2/rmw_cyclonedds

### 7. Agnocast

- **定位**：Autoware 基金会维护的 rclcpp 兼容中间件，目标是在不放弃 ROS 2 编程模型的前提下实现"任意 ROS 消息类型"的真零拷贝。
- **机制**：三件事配合——`LD_PRELOAD` 的 heaphook 把所有堆分配重定向到一段固定虚拟地址区间，这段区间背后是共享内存；订阅者把发布者的堆按相同偏移只读映射到自己地址空间，于是消息里的裸指针跨进程依然有效；引用计数与发布队列放进内核模块（`agnocast_kmod`），用系统调用做事务性更新，进程异常退出也能回收。**没有序列化**。
- **接入 ROS 2**：逐话题把 `rclcpp::Publisher` / `Subscription` 换成 `agnocast::` 版本，智能指针用 `agnocast::ipc_shared_ptr`；启动文件里配 `LD_PRELOAD`，ComposableNode 用 Agnocast 的 executor。与普通 ROS 2 节点通过 bridge 互通（默认开启，`AGNOCAST_BRIDGE_MODE=on`）。
- **主要限制**：仅 Linux + C++（Humble/Jazzy，Ubuntu 22.04/24.04）；必须能加载内核模块，README 只声明 5.x/6.x、无版本矩阵；只在同机同一 IPC namespace 内成立，跨机必须过 bridge 且那一跳是一次完整拷贝；两端内存布局必须逐字节一致（容器里 `_GLIBCXX_USE_CXX11_ABI` 不一致会静默读出错误数据）；一个话题只能有一种消息类型；不支持 Actions 与 Lifecycle，Services 仍是实验性。
- **资源开销的位置**：引用计数和队列操作在内核态，用户态路径比别人短，但每次借用/释放都是一次系统调用，多读者扇出时的开销需要按读者数评估。
- **工具**：`ros2agnocast` 包提供 `ros2 topic list_agnocast` / `info_agnocast` / `echo_agnocast` / `record_agnocast` 等动词，以及 `ros2 agnocast` 顶层命令。
- **资料**：https://github.com/autowarefoundation/agnocast ；文档站 https://autowarefoundation.github.io/agnocast_doc/ ；论文（ISORC 2025）https://arxiv.org/abs/2506.16882
